## 1. Модель роста: почему пустая карта — главный риск

Hive — продукт с **локальными сетевыми эффектами**: ценность для пользователя определяется не общим числом зарегистрированных, а количеством активных жал в его видимой области карты. TTL 4 часа усиливает эффект: контент испаряется, и при низкой плотности пустая карта — состояние по умолчанию, а не исключение.

Следствие для запуска: 10 000 пользователей, размазанных по стране, дают пустую карту; 300 пользователей на одном кампусе дают живую. Поэтому платформа обязана поддерживать **точечный (атомарный) запуск** и **продуктовые компенсации низкой плотности**, а не только «больше трафика».

### 1.1 Каналы и что каждый требует от backend

| Канал / модель привлечения                            | Суть                                                                          | Требование к backend                                                      |
| ----------------------------------------------------- | ----------------------------------------------------------------------------- | ------------------------------------------------------------------------- |
| **Атомарная сеть** (кампус, район, квартал)           | Один гео-кластер вместо страны; расширение только после достижения плотности  | Зоны и метрика плотности (§3), метрики по зоне (§G12), гео-вейтлист (§G8) |
| **Событийные запуски** (фестиваль, матч, день города) | Событие даёт естественную концентрацию людей в пространстве и времени         | Кампании с гео и временным окном (§G7), пуш по зоне (§G10)                |
| **Временная концентрация** («час улья»)               | Публикации собираются в предсказуемое окно — карта выглядит как при 10× базе  | Кампании (§G7), бонус к TTL внутри окна                                   |
| **Ценность при нуле других** (single-player)          | Личный архив, карта своих моментов, эхо своих мест                            | `/auth/me/stings`, `/auth/me/hives` (есть), эхо (§G2), достижения (§G5)   |
| **Сидинг контента**                                   | Команда, локальные фотографы, партнёрские заведения наполняют выбранный район | Партнёрские аккаунты и квоты (§G11)                                       |
| **Инвайты и вейтлист**                                | «Город откроется при N заявках»; приглашение друга напрямую оживляет карту    | Инвайты, атрибуция, вейтлист (§G8)                                        |
| **Существующие сообщества** (чаты домов, кампусов)    | Самый дешёвый канал гиперлокального трафика                                   | Инвайт-ссылки с атрибуцией (§G8)                                          |
| **Виральность контента наружу**                       | Ссылка на жало с веб-превью, работающая без установки                         | Публичная share-страница с OG (§G9)                                       |
| **Амбассадоры**                                       | Ответственный за район/кампус с квотой                                        | Метрики по зоне (§G12), партнёрский аккаунт (§G11)                        |
| **Платный трафик**                                    | Включается **последним**, только в зонах с достигнутой плотностью             | Метрики плотности как gate (§2, §G12)                                     |

Отдельно — механики, полностью лежащие на клиенте: камера-first онбординг (**G6**) и активное пустое состояние карты (клиентская часть **G5**). Их ТЗ — в `RN_GROWTH_TZ.md`.

### 1.2 Арифметика плотности (обоснование приоритетов)

Число активных жал в зоне в произвольный момент:

```
N_active ≈ U_zone × p × (TTL_hours / 24)

U_zone  — ежедневно активных пользователей в зоне
p       — среднее число публикаций на активного пользователя в сутки
```

Обратная задача — сколько нужно DAU в зоне, чтобы во вьюпорте было `D_target = 20` жал при `p = 0.5`:

| TTL  | Требуемый DAU в зоне |
| ---- | -------------------- |
| 4 ч  | ~240                 |
| 8 ч  | ~120                 |
| 24 ч | ~40                  |
| 72 ч | ~13                  |

Вывод, определяющий порядок работ: **динамический TTL (§G1) — самый сильный рычаг cold start**, дешевле любого трафика. Далее идут механики, которые не дают карте выглядеть мёртвой (§G2, §G3, §G4), и только потом виральные петли (§G8, §G9) и пуши (§G10).

## 2. Метрики и определения

| Метрика                    | Определение                                                                          | Целевое значение на раннем этапе        |
| -------------------------- | ------------------------------------------------------------------------------------ | --------------------------------------- |
| `viewportDensity`          | Число активных жал + активных ульев в bbox первого запроса `/stings/nearby` в сессии | медиана ≥ 20 в зонах со статусом `open` |
| `emptySessionRate`         | Доля сессий, где первый `/stings/nearby` вернул 0 жал и 0 активных ульев             | < 30% (цель < 20%)                      |
| `zoneDau`                  | Уникальные пользователи с ≥1 запросом `/stings/nearby` в зоне за сутки               | ≥ 40 при TTL 24 ч (см. §1.2)            |
| `postsPerActiveUser` (`p`) | Публикации / активные пользователи за сутки в зоне                                   | ≥ 0.4                                   |
| `zoneRetentionD7`          | D7-retention когорты по **зоне первой сессии**, не по стране                         | ≥ 20%                                   |
| `kFactor`                  | Принятые инвайты / пригласивших пользователей за 14 дней                             | ≥ 0.4                                   |
| `pushOpenRate`             | Открытия / доставленные пуши по типу                                                 | ≥ 8%                                    |

Правила измерения:

- Retention и плотность считаются **по зоне**, а не в среднем по базе: средние числа смешивают живой кампус с мёртвой географией и скрывают, работает ли модель.
- `emptySessionRate` считается по факту первого запроса карты в сессии, **до** расширения радиуса (§G3), иначе метрика самообманывается.
- Гейт на платный трафик и на расширение в новую зону: `viewportDensity` медиана ≥ 20 **и** `zoneRetentionD7` ≥ 20% в текущей зоне.

## 3. Фундамент: зоны и расчёт плотности

Все механики роста опираются на общее понятие зоны. Реализуется один раз и переиспользуется.

### 3.1 Гео-индексация

- Ячейка зоны — **H3 res 8** (~0.46 км², ребро ~460 м) через `h3-js`. Альтернатива без новой зависимости — geohash precision 6; выбор фиксируется один раз и не смешивается.
- Ячейка обзора города — **H3 res 5** (агрегация для §G4).
- У каждого `Sting` при создании денормализуются `zoneId` (res 8) и `overviewCellId` (res 5). Пересчёт постфактум не делается.

### 3.2 Модель `Zone`

```ts
interface Zone {
  id: string; // H3 index res 8
  overviewCellId: string; // H3 index res 5
  center: GeoPoint;
  status: 'open' | 'waitlist'; // §G8; по умолчанию 'open'
  // Скользящие агрегаты, обновляются воркером (§3.3)
  stings24h: number;
  activeStings: number; // не истёкших на момент пересчёта
  dau24h: number;
  ttlSec: number; // текущий TTL для новых жал (§G1)
  waitlistCount: number; // §G8
  updatedAt: string;
}
```

Индексы: `{ id: 1 }` (unique), `{ overviewCellId: 1 }`, `{ updatedAt: 1 }`.

Дополнительные индексы на `stings`: `{ zoneId: 1, expiresAt: 1 }`, `{ zoneId: 1, createdAt: -1 }`, существующий 2dsphere по `location` сохраняется.

### 3.3 Воркер пересчёта

- Периодичность: раз в 5 минут для зон с активностью за последние 24 ч, раз в час для остальных.
- Считает `stings24h`, `activeStings`, `dau24h`, пересчитывает `ttlSec` по таблице §G1.
- Идемпотентен, работает пачками (`bulkWrite`), не блокирует запросы карты.
- Зона создаётся лениво: при первой публикации или первом запросе карты в ячейке.

**DoD фундамента:** для любой точки на карте сервер за один вызов отдаёт `zoneId`, актуальные агрегаты и `ttlSec`; пересчёт не влияет на p95 `/stings/nearby`.

## G1 — Динамический TTL по плотности

**Задача:** в разреженных зонах жало живёт дольше, в плотных — остаётся «здесь и сейчас». Это устраняет корень проблемы пустой карты без привлечения трафика.

### Правила

| `stings24h` в зоне | `ttlSec`       | Смысл                                           |
| ------------------ | -------------- | ----------------------------------------------- |
| ≥ 60               | 14 400 (4 ч)   | Базовый режим, карта живая и быстро обновляется |
| 20–59              | 28 800 (8 ч)   | Разогрев зоны                                   |
| 5–19               | 86 400 (24 ч)  | Холодная зона                                   |
| 0–4                | 259 200 (72 ч) | Пустая зона, первопроходцы                      |

- TTL вычисляется **в момент публикации** и фиксируется в `expiresAt`. Пересчёт TTL уже опубликованных жал **запрещён**: иначе клиентский `useCountdown` показывает неправду, а `sting:expired` конфликтует с локальным таймером.
- Кампании (§G7) могут добавить `ttlBonusSec`, но итоговый TTL не превышает 72 ч.
- Приватность: длинный TTL = долгая экспозиция локации. Компенсации: автор всегда может удалить жало (`DELETE /stings/:id`), фактический TTL показывается пользователю **до** публикации (см. `RN_GROWTH_TZ.md` §G1), значение `ttlSec` возвращается в ответе публикации.

### Контракт

`POST /stings` — ответ дополняется:

```json
{
  "sting": { "...": "...", "expiresAt": "2026-09-08T12:00:00.000Z" },
  "ttlSec": 86400,
  "zone": { "id": "8811aa...", "status": "open", "ttlSec": 86400 }
}
```

Новый эндпоинт для предпросмотра TTL до съёмки:

```
GET /zones/current?lat={number}&lng={number}
```

```json
// Response 200
{
  "zone": {
    "id": "8811aa...",
    "status": "open",
    "ttlSec": 86400,
    "activeStings": 3,
    "isFirstEver": true
  }
}
```

`isFirstEver` — в зоне не было ни одного жала за всё время (используется механикой первооткрывателя, §G5).

**DoD:** публикация в пустой зоне даёт `expiresAt` +72 ч, в плотной — +4 ч; `GET /zones/current` до съёмки возвращает то же значение, что применится при публикации (расхождение допустимо только если зона переехала в другой bucket между вызовами).

## G2 — Эхо: слой истёкших жал

**Задача:** карта должна показывать «здесь бывают люди», даже когда прямо сейчас активного контента нет. Эхо — агрегированный след истёкших жал, без фото и без авторства.

### Правила

- Эхо **агрегируется по ячейке**, а не по отдельному жалу: наружу отдаётся `{ cellId, center, count, lastSeenAt }`. Это одновременно приватность и маленький payload.
- Ячейка эха — H3 res 9 (~0.1 км²), центр ячейки, не реальные координаты жала. Точные координаты истёкших жал наружу не отдаются никогда.
- Порог публикации: ячейка попадает в ответ при `count >= 1`, но координаты всегда снапятся к центру ячейки.
- Retention: 7 суток, затем удаление. Отдельная коллекция `sting_echoes` с TTL-индексом Mongo по `expiresAt`.
- Исключения: жало, удалённое автором (`DELETE /stings/:id`) до истечения, эхо **не оставляет**; пользователь с `settings.allowEcho = false` не попадает в эхо вовсе.
- Эхо не открывается, не содержит `imageUrl`/`thumbnailUrl`, не содержит `authorId`.

### Модель

```ts
interface StingEchoCell {
  cellId: string; // H3 res 9
  zoneId: string; // H3 res 8
  center: GeoPoint; // центр ячейки
  count: number; // истёкших жал за окно retention
  lastSeenAt: string; // createdAt последнего истёкшего жала
  expiresAt: string; // lastSeenAt + 7 суток, TTL-индекс
}
```

Запись/инкремент — в том же джобе, который истекает жала и рассылает `sting:expired`.

### Контракт

`GET /stings/nearby` получает новый необязательный параметр:

```
includeEchoes: boolean (default false)
```

```json
// Response 200 (при includeEchoes=true)
{
  "stings": [],
  "hives": [],
  "echoes": [
    {
      "cellId": "8911aa...",
      "center": { "lat": 55.75, "lng": 37.61 },
      "count": 4,
      "lastSeenAt": "2026-09-06T19:12:00.000Z"
    }
  ]
}
```

Лимит: не более 300 ячеек эха на ответ, при превышении — агрегация до H3 res 8.

**DoD:** после истечения жал в области `includeEchoes=true` возвращает ячейки с корректным `count`; ответ не содержит ни ссылок на фото, ни `authorId`; при `allowEcho=false` жала автора в эхо не появляются.

## G3 — Адаптивный радиус и ближайшее жало

**Задача:** пустой вьюпорт не должен означать пустой ответ. Сервер сам расширяет область, пока не наберёт минимум результатов, и умеет сказать, где ближайшая жизнь.

### Контракт

`GET /stings/nearby` — новые необязательные параметры:

```
minResults:  number (default 0, max 50)   — целевое число жал
maxRadiusM:  number (default 50000)       — предел расширения
```

Алгоритм: начать с переданного bbox; пока `stings.length < minResults` и радиус < `maxRadiusM` — расширять bbox шагами ×2 (не более 5 шагов). Ответ сообщает, что фактически применилось:

```json
{
  "stings": [],
  "hives": [],
  "appliedBounds": { "swLat": 0, "swLng": 0, "neLat": 0, "neLng": 0 },
  "expanded": true,
  "appliedRadiusM": 12000
}
```

Новый эндпоинт:

```
GET /stings/nearest?lat={number}&lng={number}&limit={1..10}
```

```json
// Response 200
{
  "stings": [ { "...": "..." } ],
  "distanceM": 11840
}

// Response 200 — во всей стране активных жал нет
{ "stings": [], "distanceM": null }
```

Реализация — `$geoNear` по 2dsphere, только активные жала, лимит по `maxDistance` 300 км.

Совместимость: без новых параметров поведение `/stings/nearby` не меняется (`expanded: false`, `appliedBounds` = переданный bbox). Это важно, чтобы текущий клиент не сломался.

**DoD:** в пустом районе запрос с `minResults=10` возвращает жала из расширенной области и честный `appliedRadiusM`; `/stings/nearest` находит ближайшее жало в другом городе с корректной дистанцией; p95 обоих запросов < 300 мс на индексах.

## G4 — Обзор города на дальнем зуме

**Задача:** при отзуме карта не должна выглядеть мёртвой. Публикация остаётся гиперлокальной, но смотреть можно агрегаты по городу и стране.

### Контракт

```
GET /map/overview?swLat&swLng&neLat&neLng&zoom={number}
```

```json
// Response 200
{
  "clusters": [
    {
      "cellId": "8511aa...",
      "center": { "lat": 55.75, "lng": 37.61 },
      "radiusM": 9000,
      "activeStingsCount": 42,
      "activeHivesCount": 3,
      "label": "Москва"
    }
  ],
  "resolution": 5
}
```

- `resolution` выбирается сервером по `zoom`: res 5 для страны, res 6 для города. Клиент не диктует разрешение.
- Фото и координаты отдельных жал не отдаются — только агрегаты. Это защищает и приватность, и трафик.
- `label` — опционально, из реверс-геокодинга кэшированно по ячейке (может быть `null`; клиент обязан это выдержать).
- Кэш ответа 60 с (агрегаты и так пересчитываются воркером §3.3).

**DoD:** при bbox размером со страну ответ возвращает ≤ 500 кластеров за < 200 мс и не содержит `imageUrl`.

## G5 — Механика первооткрывателя

**Задача:** превратить пустоту из дефекта в повод опубликовать. Первое жало в зоне — событие с наградой.

### Правила

- Награда `zone_first` выдаётся **один раз на зону глобально** — первому жалу в этой H3 res 8 за всю историю.
- Награда `zone_revival` — первое жало в зоне, где не было активности ≥ 14 суток. Может выдаваться повторно, но не чаще одного раза в 14 суток на зону.
- Награды не выдаются: партнёрским/официальным аккаунтам (§G11), жалам, не прошедшим анти-спуфинг (`TECH_DOCS.md` §5.3), и при `accuracy` хуже 50 м — иначе бейджи станут призом за спуфинг GPS.
- Награда фиксируется атомарно вместе с созданием жала (транзакция / `findOneAndUpdate` с условием), иначе два одновременных первых жала получат одну награду дважды.

### Модель

```ts
interface Award {
  id: UUID;
  userId: UUID;
  type: 'zone_first' | 'zone_revival';
  zoneId: string;
  stingId: UUID;
  center: GeoPoint;
  createdAt: string;
}
```

Индексы: `{ type: 1, zoneId: 1 }` (unique для `zone_first`), `{ userId: 1, createdAt: -1 }`.

### Контракт

`POST /stings` — ответ дополняется (поле опционально, отсутствует если наград нет):

```json
{
  "sting": { "...": "..." },
  "ttlSec": 259200,
  "awards": [{ "type": "zone_first", "zoneId": "8811aa...", "createdAt": "..." }]
}
```

```
GET /auth/me/awards?cursor&limit   → { "awards": Award[], "nextCursor": string | null }
GET /auth/me/stats                 → дополняется полем "awards": number
```

**DoD:** первое жало в незатронутой зоне возвращает `awards[0].type = "zone_first"`; второе жало в той же зоне — пустой список; параллельные публикации не создают дубликат награды.

## G7 — Кампании и «час улья»

**Задача:** концентрировать активность во времени и вокруг событий. При малой базе это единственный способ получить «плотную» карту без роста числа пользователей.

### Модель

```ts
interface Campaign {
  id: UUID;
  kind: 'hive_hour' | 'event';
  title: string; // локализованные строки — на клиенте по ключу
  i18nKey: string; // напр. 'campaign.hiveHour'
  geo: { type: 'radius'; center: GeoPoint; radiusM: number } | { type: 'zones'; zoneIds: string[] };
  startsAt: string;
  endsAt: string;
  recurrence: 'none' | 'daily' | 'weekly';
  ttlBonusSec: number; // 0 или бонус к TTL публикаций внутри окна
  pushEnabled: boolean;
  createdAt: string;
}
```

- `hive_hour` — регулярное окно (например 19:00–20:00 локального времени зоны), `recurrence: 'daily'`.
- `event` — разовое событие (фестиваль, матч) с гео-радиусом.
- Публикация внутри активной кампании получает `ttlBonusSec` (итог не выше 72 ч, §G1) и помечается `campaignId`.

### Контракт

```
GET /campaigns/active?lat={number}&lng={number}
```

```json
// Response 200
{
  "campaigns": [
    {
      "id": "...",
      "kind": "hive_hour",
      "i18nKey": "campaign.hiveHour",
      "startsAt": "2026-09-07T19:00:00.000Z",
      "endsAt": "2026-09-07T20:00:00.000Z",
      "ttlBonusSec": 14400,
      "participantsCount": 12
    }
  ]
}
```

WebSocket (формат событий — `TECH_DOCS.md` §4):

| Event              | Payload                  | Когда                                         |
| ------------------ | ------------------------ | --------------------------------------------- |
| `campaign:started` | `{ campaign: Campaign }` | Кампания стала активной в подписанном регионе |
| `campaign:ended`   | `{ campaignId: UUID }`   | Окно закрылось                                |

Пуш о старте кампании — через §G10, тип `campaign_started`, только пользователям с активностью в затронутых зонах за 14 суток.

Админ-часть: создание кампаний — защищённый эндпоинт `POST /admin/campaigns` (роль `admin`), UI не требуется на MVP.

**DoD:** активная кампания приходит в `/campaigns/active` и по WS; публикация внутри окна получает бонусный TTL; после `endsAt` кампания исчезает из ответа и приходит `campaign:ended`.

## G8 — Инвайты, атрибуция, гео-вейтлист

**Задача:** дать пользователю прямой способ оживить свою карту (позвать тех, кто рядом) и собрать спрос там, где плотность будет достаточной.

### 8.1 Инвайты

```ts
interface Invite {
  code: string; // 8 символов, base32 без похожих символов
  ownerId: UUID;
  zoneId: string | null; // зона владельца на момент создания
  usesLimit: number; // по умолчанию 5
  usesCount: number;
  createdAt: string;
  expiresAt: string; // +30 суток
}
```

```
POST /invites            → { "code": "H7K2M9QA", "url": "https://hive.app/i/H7K2M9QA", "usesLeft": 5, "expiresAt": "..." }
GET  /invites/me         → { "invites": Invite[], "acceptedCount": number, "usesLeft": number }
GET  /invites/{code}     → { "valid": boolean, "ownerUsername": string | null, "zoneCenter": GeoPoint | null }   // публичный, без токена
```

- Квота: 5 использований на пользователя, +2 за каждого принятого приглашённого (потолок 25). Смысл — вознаграждать работающие приглашения, а не рассылку кодов.
- `GET /invites/{code}` не раскрывает email и точные координаты (только центр зоны res 8).

### 8.2 Атрибуция при регистрации

`POST /auth/register` и `POST /auth/google` получают необязательное поле:

```json
{ "inviteCode": "H7K2M9QA" }
```

- Невалидный/просроченный код **не ломает регистрацию**: пользователь создаётся, код игнорируется, в логах — предупреждение. Ошибку клиенту не возвращать.
- В `users` пишутся `invitedByUserId`, `invitedInviteCode`, `signupZoneId` (зона первой сессии, если передана геолокация или определена по первому запросу карты).
- Начисление бонуса пригласившему — только после того, как приглашённый **опубликовал первое жало** (защита от фарма пустыми регистрациями).

### 8.3 Гео-вейтлист (по умолчанию выключен)

Механика закрывается фича-флагом `WAITLIST_ENABLED` и включается только осознанно: она превращает пустоту в ожидание, но она же режет входящий трафик. По умолчанию все зоны `open`.

```
POST /waitlist            { "lat": 0, "lng": 0, "email": "user@example.com" }
      → { "zoneId": "...", "status": "waitlist", "currentCount": 128, "threshold": 300 }

GET  /zones/current?lat&lng  (§G1)  → дополняется полями status / waitlistCount / threshold
```

- Порог открытия зоны — `WAITLIST_THRESHOLD` (по умолчанию 300 заявок в зоне res 8 или её соседях).
- При достижении порога зона переводится в `open`, всем заявкам уходит письмо/пуш (§G10, тип `zone_opened`).
- Anti-enumeration: ответ одинаков независимо от того, была ли уже заявка с этим email.
- Один email и один `deviceId` — одна заявка на зону.

**DoD:** приглашённый по ссылке пользователь получает `invitedByUserId`; бонус пригласившему начисляется только после первой публикации приглашённого; при `WAITLIST_ENABLED=false` все эндпоинты вейтлиста отвечают `404 FEATURE_DISABLED`, а `zones/current` всегда `open`.

## G9 — Публичный шаринг жала

**Задача:** дать контенту выходить за пределы приложения — ссылка должна открываться у человека без установленного Hive и вести на установку.

### Контракт

- В `Sting` DTO добавляется `shareUrl: string | null` (null — если автор запретил шаринг).
- Публичная страница (не API, отдаётся сервером как HTML):

```
GET /share/stings/{id}
```

Требования к странице:

| Состояние жала            | Что показывается                                                                                                                                                               |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Активно, шаринг разрешён  | `thumbnailUrl` (не оригинал), название места по реверс-геокоду ячейки res 8, таймер до истечения, кнопки «Открыть в Hive» (deep link `hiveapp://sting/{id}`) и ссылки на сторы |
| Истекло                   | Страница «жало истекло» без фото + гео-тизер («в этом районе за неделю было N моментов») и кнопка установки                                                                    |
| Шаринг запрещён / удалено | 404-страница без утечки существования                                                                                                                                          |

- OG-теги обязательны: `og:title`, `og:description`, `og:image` (thumbnail), `og:url`, `twitter:card=summary_large_image` — иначе ссылка в мессенджерах выглядит мёртвой и канал не работает.
- Точные координаты в HTML и в OG не публикуются: только центр ячейки res 8 и человекочитаемое название района.
- Настройка автора: `PATCH /auth/me/settings { "allowSharing": boolean }` (по умолчанию `true`), плюс `allowEcho` из §G2 в том же эндпоинте.
- Отдельный лимит: не более 60 запросов/мин на IP к `/share/*`, кэш HTML 60 с.

**DoD:** ссылка, отправленная в Telegram/WhatsApp, разворачивается в превью с фото и заголовком; после истечения жала та же ссылка отдаёт корректную страницу без фото; при `allowSharing=false` `shareUrl` = `null` и страница отдаёт 404.

## G10 — Push-уведомления удержания

**Задача:** возвращать пользователя в приложение поводами, которые не зависят от текущей плотности карты.

### Модель и контракт

```ts
interface Device {
  id: UUID;
  userId: UUID;
  expoPushToken: string; // ExponentPushToken[...]
  platform: 'ios' | 'android';
  deviceId: string; // стабильный идентификатор установки
  locale: 'ru' | 'en';
  timezone: string; // IANA, для quiet hours
  lastSeenAt: string;
  createdAt: string;
}

interface NotificationSettings {
  reactions: boolean; // default true
  nearbyActivity: boolean; // default true
  campaigns: boolean; // default true
  expiringSting: boolean; // default false
  inviteAccepted: boolean; // default true
}
```

```
POST   /devices                        { expoPushToken, platform, deviceId, locale, timezone } → 204
DELETE /devices/{deviceId}             → 204   (вызывается при logout)
GET    /notifications/settings         → { settings: NotificationSettings }
PATCH  /notifications/settings         { ...partial } → { settings: NotificationSettings }
```

`expoPushToken` уникален: при повторной регистрации того же `deviceId` запись обновляется, а не дублируется.

### Типы уведомлений

| Тип                | Триггер                                                                                                | Настройка        | Приоритет                                             |
| ------------------ | ------------------------------------------------------------------------------------------------------ | ---------------- | ----------------------------------------------------- |
| `sting_reaction`   | Лайк на жало пользователя                                                                              | `reactions`      | Высокий, не батчится (мгновенная соц. обратная связь) |
| `nearby_activity`  | Улей активировался (`activeStingsCount` достиг порога) в зоне, где пользователь публиковал за 14 суток | `nearbyActivity` | Средний, не чаще 1 раза в сутки на пользователя       |
| `campaign_started` | Старт кампании в релевантной зоне (§G7)                                                                | `campaigns`      | Средний                                               |
| `sting_expiring`   | 30 минут до истечения жала, у которого есть реакции                                                    | `expiringSting`  | Низкий, по умолчанию выключен                         |
| `invite_accepted`  | Приглашённый опубликовал первое жало                                                                   | `inviteAccepted` | Средний                                               |
| `zone_opened`      | Зона вышла из вейтлиста (§G8)                                                                          | всегда           | Высокий, разовое                                      |

### Правила отправки

- **Гео-таргетинг только по опубликованным жалам.** Запрещено использовать непрерывный трекинг локации или последний известный `region` карты: сервер знает зоны пользователя исключительно из его публикаций. Это и приватность, и отсутствие фонового GPS в приложении.
- Лимит: не более **3 пушей в сутки** на пользователя (кроме `sting_reaction` и `zone_opened`), дедупликация по `(userId, type, entityId)` в пределах 24 ч.
- Quiet hours: 22:00–09:00 по `timezone` устройства — отправка откладывается до 09:00, `sting_expiring` в этом окне не отправляется вовсе.
- Транспорт: Expo Push API, батчи ≤ 100 сообщений, обязательная обработка **push receipts**; при `DeviceNotRegistered` — удаление записи `Device`.
- Payload обязателен для диплинка: `data: { type, deeplink }`, где `deeplink` — `hiveapp://sting/{id}`, `hiveapp://campaign/{id}` или `hiveapp://(tabs)`.
- Текст уведомления собирается на сервере по `locale` устройства (ru/en), ключи копий фиксируются вместе с i18n клиента.

**DoD:** лайк на жало приводит к пушу на реальное устройство с dev/preview-сборкой; тап открывает нужный экран; выключенный тумблер в настройках останавливает соответствующий тип; невалидные токены исчезают из базы после обработки receipts; в quiet hours пуши не приходят.

## G11 — Партнёрские аккаунты и сидинг

**Задача:** дать команде, локальным фотографам и партнёрским заведениям легальный способ наполнять выбранный район, не притворяясь обычными пользователями.

### Правила

- `users.accountType: 'personal' | 'partner' | 'official'` (по умолчанию `personal`), выдаётся только админом (`POST /admin/users/{id}/account-type`).
- В `Sting` DTO добавляется `authorAccountType` — клиент показывает бейдж (`RN_GROWTH_TZ.md` §G11). **Фейковые «живые» аккаунты запрещены**: в гео-продукте пользователь физически находится в том же месте и несоответствие обнаруживается сразу, а доверие после этого не восстанавливается.
- Партнёрские аккаунты **не освобождаются** от анти-спуфинга (`TECH_DOCS.md` §5.3): сидинг — это реальная съёмка на месте, а не загрузка архива. Это осознанное ограничение производительности сидинга в пользу достоверности карты.
- Отдельные rate limits: `partner` — 30 публикаций/сутки, `official` — 100/сутки (у `personal` действует текущий лимит).
- Награды первооткрывателя (§G5) партнёрам не начисляются.
- Метрики (§G12) обязаны считаться в двух разрезах: включая и исключая партнёрский контент. Иначе сидинг «нарисует» плотность и метрика перестанет отражать реальную сеть.

**DoD:** партнёрский аккаунт публикует с повышенным лимитом, его жала помечены `authorAccountType` в API, дашборд плотности показывает раздельные значения с сидингом и без.

## G12 — Аналитика роста

**Задача:** решения о расширении и о включении платного трафика принимаются по плотности и удержанию в зоне, а не по общему числу установок.

### Приём событий

```
POST /analytics/events
```

```json
{
  "events": [
    {
      "name": "session_start",
      "occurredAt": "2026-09-07T18:00:00.000Z",
      "zoneId": "8811aa...",
      "props": { "stingsInViewport": 0, "hivesInViewport": 0, "echoes": 3, "expanded": false }
    }
  ]
}
```

- Батч до 50 событий, тело до 64 КБ, идемпотентность по `(userId, name, occurredAt)`.
- Работает и без авторизации (для событий до регистрации) — тогда идентификация по `deviceId`; персональные данные в `props` запрещены.
- Обязательный минимум событий: `app_open`, `session_start`, `map_empty_shown`, `empty_cta_tap`, `nearest_sting_opened`, `first_sting_published`, `sting_published`, `invite_created`, `invite_accepted`, `share_opened`, `push_received`, `push_opened`, `campaign_banner_shown`, `waitlist_submitted`.

### Агрегаты

```
GET /admin/metrics/density?zoneId&from&to      → медиана viewportDensity, emptySessionRate, zoneDau, p
GET /admin/metrics/retention?zoneId&cohort     → D1/D7/D30 по зоне первой сессии
GET /admin/metrics/growth?from&to              → kFactor, инвайты, share-переходы, установки по зонам
```

Роль `admin`, ответы кэшируются на 5 минут.

**DoD:** для выбранной зоны дашборд показывает медианную плотность вьюпорта, долю пустых сессий и D7 по когорте; значения совпадают с ручной выборкой из сырых событий.

## 15. Rate limits и антифрод (сводно)

| Ресурс                   | Лимит                                                         | Причина                                     |
| ------------------------ | ------------------------------------------------------------- | ------------------------------------------- |
| `POST /stings`           | текущий лимит; `partner` 30/сут, `official` 100/сут           | Сидинг vs спам                              |
| `POST /invites`          | 10/сутки на пользователя                                      | Фарм кодов                                  |
| Принятие инвайта         | Бонус только после первой публикации приглашённого            | Фарм пустыми регистрациями                  |
| `POST /waitlist`         | 1 заявка на (email, зона) и на (deviceId, зона), 20/час на IP | Накрутка порога открытия зоны               |
| `GET /share/*`           | 60/мин на IP                                                  | Скрейпинг контента                          |
| `POST /analytics/events` | 120 запросов/час на устройство                                | Мусорный трафик                             |
| `POST /devices`          | 20/сутки на пользователя                                      | Мусорные токены                             |
| Награды §G5              | Только при пройденном анти-спуфинге и `accuracy ≤ 50 м`       | Бейдж не должен быть призом за подделку GPS |

Общее правило: ни одна механика роста не ослабляет проверки публикации из `TECH_DOCS.md` §5.3. Рост, купленный ценой недоверия к карте, для гео-продукта убыточен.

## 17. Риски

- **Длинный TTL как утечка приватности.** 72 часа на карте — это долгая экспозиция места съёмки. Митигация: агрегация эха, удаление автором, честное отображение TTL до публикации, `allowEcho`/`allowSharing`.
- **Ретроактивное изменение TTL.** Соблазн «продлить всё в пустой зоне» ломает клиентские таймеры и `sting:expired`. Запрещено спецификацией (§G1).
- **Метрика, отравленная сидингом.** Без разреза «с партнёрами / без» команда будет принимать решения о расширении по нарисованной плотности (§G11).
- **Пуши как причина удаления приложения.** Больше 3 пушей в сутки и игнорирование quiet hours дают обратный эффект. Лимиты — часть контракта, а не рекомендация.
- **Вейтлист режет трафик.** Включённый по умолчанию гейт может стоить дороже, чем пустая карта. Поэтому фича-флаг и default `open`.
- **Расширение области в `/stings/nearby` без индексов** превратит карту в медленную. Индексы `{ zoneId: 1, expiresAt: 1 }` и 2dsphere обязательны до включения `minResults`.
- **Гео-таргетинг пушей по «домашней» зоне** — потенциально чувствительная деанонимизация. Разрешён только по зонам публикаций и не точнее res 8.

## 18. Приёмочный чек-лист

- [ ] Публикация в пустой зоне: `ttlSec = 259200`, в плотной — `14400`; `GET /zones/current` совпадает с фактом
- [ ] TTL уже созданных жал не меняется ни воркером, ни кампанией
- [ ] `includeEchoes=true` возвращает ячейки без `imageUrl`, `thumbnailUrl` и `authorId`
- [ ] Удалённое автором жало не оставляет эха; `allowEcho=false` исключает пользователя из эха
- [ ] `minResults=10` в пустом районе даёт расширенный `appliedBounds` и честный `appliedRadiusM`
- [ ] `GET /stings/nearest` возвращает `distanceM` и `null` при полном отсутствии жал
- [ ] `GET /map/overview` на bbox страны — ≤ 500 кластеров, < 200 мс, без ссылок на фото
- [ ] `zone_first` выдаётся один раз на зону при параллельных публикациях
- [ ] Награды не выдаются при `accuracy > 50 м`, при провале анти-спуфинга и партнёрам
- [ ] Инвайт: невалидный код не ломает регистрацию; бонус только после первой публикации приглашённого
- [ ] Share-ссылка разворачивается в превью в Telegram и WhatsApp; истёкшее жало отдаёт страницу без фото
- [ ] `allowSharing=false` → `shareUrl: null` и 404 на публичной странице
- [ ] Пуш о реакции доходит на iOS и Android (dev/preview build), `data.deeplink` открывает жало
- [ ] Quiet hours соблюдаются по timezone устройства; лимит 3/сутки не превышается
- [ ] `DeviceNotRegistered` из receipts удаляет токен
- [ ] Кампания «час улья» даёт бонусный TTL и приходит по WS и пушем
- [ ] `WAITLIST_ENABLED=false`: эндпоинты вейтлиста отдают `404 FEATURE_DISABLED`, все зоны `open`
- [ ] `/admin/metrics/density` сходится с ручной выборкой; есть разрез без партнёрского контента
- [ ] `openapi.yaml` и `TECH_DOCS.md` описывают все новые пути, схемы и WS-события

## 19. Вне скоупа

- Рекомендательная лента и алгоритмическое ранжирование жал
- Полноценный admin-UI (эндпоинты `/admin/*` вызываются вручную или из служебного скрипта)
- Email-рассылки помимо OTP и `zone_opened`
- Атрибуция платных установок (SKAdNetwork / Install Referrer) и интеграция MMP
- Модерация партнёрского контента как отдельный воркфлоу (используется существующая модерация публикаций)
- Импорт внешнего контента (карты, соцсети) как источник сидинга — противоречит правилу «только съёмка на месте»
- Внутриигровая экономика, уровни, лидерборды (кроме наград §G5)
